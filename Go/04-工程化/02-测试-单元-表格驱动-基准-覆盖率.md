# 02 - 测试：单元、表格驱动、基准、覆盖率

> 从 C++ 的 GTest 到 Go testing 标准库：约定优于配置，表格驱动是 Go 的灵魂测试法

---

## 一、简述

Go 把测试框架内置为标准库 `testing`，**零配置**、约定驱动：文件以 `_test.go` 结尾，函数名 `TestXxx(t *testing.T)` 即被测对象。不需要 GTest 那样的宏和注册表，`go test` 一条命令跑全部测试。

C++ 开发者上手 GTest 要经历「链接 gtest、写 TEST 宏、配 CMake、起 runner」；Go 则是「建 `_test.go`、写 `func TestXxx(t *testing.T)`、`go test`」。**表格驱动测试（table-driven tests）**是 Go 社区最推崇的测试形态——本质是把断言与数据分离，让测试用例变成一张表。

> **核心要点**：`testing` 包只给了「基础骨架」（`t` 的各种方法），断言与 mock 不内置——这是 Go 的极简哲学。但配合表格驱动 + 子测试 + 基准 + 覆盖率，能覆盖绝大多数项目需求。

---

## 二、C++ 对照速查表

| 概念 | C++ | Go | 关键差异 |
|------|-----|-----|----------|
| 测试框架 | GoogleTest / Catch2（第三方） | `testing` 标准库 | 零依赖、零配置，`go test` 即跑 |
| 测试文件 | `test_xxx.cpp` | `xxx_test.go` | 命名约定即可被发现 |
| 测试用例 | `TEST(Suite, Name)` | `func TestXxx(t *testing.T)` | 编译期自动收集，无宏无注册 |
| 断言 | `EXPECT_EQ` / `ASSERT_EQ` | `t.Errorf` / `t.Fatal` | Go 里就是普通方法调用 |
| 致命 vs 非致命 | ASSERT（终止）vs EXPECT（继续） | `t.Fatal`（终止）vs `t.Errorf`（继续） | 语义一一对应 |
| 子测试 | SCOPED_TRACE 近似 | `t.Run("name", ...)` | 自带层级输出、可独立筛选运行 |
| 表格驱动 | GTEST 参数化 P 复杂 | 切片 + for 循环 | 语言特性天然支持，无需框架 |
| 基准测试 | Google Benchmark | `BenchmarkXxx(b *testing.B)` + `b.N` | benchmark 内建 |
| 覆盖率 | `-fprofile-arcs` + gcov/lcov | `go test -cover` | 一条命令带 HTML 输出 |
| 数据竞态检测 | TSan（需编译期开启） | `go test -race` | 运行时内建，跨平台 |

## 三、逐主题详解

### 3.1 单元测试最小形态

在 `calc.go` 旁边放 `calc_test.go`：

```go
// calc.go —— 被测代码
package main

import "errors"

func Divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("除数不能为 0")
    }
    return a / b, nil
}
```

```go
// calc_test.go —— 测试代码（同包 main，或换 _test 包后缀）
package main

import "testing"

func TestDivide(t *testing.T) {
    // 传入普通参数，用 t 汇报失败
    got, err := Divide(6, 3)
    if err != nil {
        t.Fatalf("不应出错: %v", err) // Fatal: 失败立即终止本测试
    }
    if got != 2 {
        t.Errorf("Divide(6,3) = %d, want 2", got) // Errorf: 失败记录但继续
    }
}
```

运行：

```bash
go test                 # 跑当前包全部测试
go test -v              # 显示每个用例名与结果
go test ./...           # 递归跑整个项目
go test -run TestDivide # 只跑名字含 TestDivide 的测试（支持正则）
```

> **C++ 对照**：`t.Fatal` ≈ `ASSERT_*`，`t.Errorf` ≈ `EXPECT_*`。区分很关键：前置条件（如 `err != nil` 后没法继续）用 Fatal，纯值比较用 Errorf。

### 3.2 表格驱动测试（Table-Driven Tests）

一个业务函数，用「用例表」覆盖多组输入输出：

```go
func TestDivideTable(t *testing.T) {
    tests := []struct {
        name string // 用例名，用于子测试与失败定位
        a, b int
        want int
        wantErr bool
    }}{
        {"正数相除", 6, 3, 2, false},
        {"负数", -6, 3, -2, false},
        {"除数为零", 6, 0, 0, true},
        {"整除得1", 5, 5, 1, false},
        {"余数截断", 7, 2, 3, false}, // Go 整数除法向零截断
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) { // 子测试：每个用例都是独立测试
            got, err := Divide(tt.a, tt.b)
            if (err != nil) != tt.wantErr {
                t.Fatalf("Divide(%d,%d) err = %v, wantErr %v", tt.a, tt.b, err, tt.wantErr)
            }
            if got != tt.want {
                t.Errorf("Divide(%d,%d) = %d, want %d", tt.a, tt.b, got, tt.want)
            }
        })
    }
}
```

跑子测试：

```bash
# 运行全部子测试
go test -v

# 只运行指定子测试（外层/内层用 / 分隔）
go test -run 'TestDivideTable/正数相除'

# 用正则跑一组
go test -run 'TestDivideTable/(正数|负数)'
```

> **C++ 对照**：这套写法就是 GTest 参数化测试（`TEST_P` / `INSTANTIATE_TEST_SUITE_P`）的手搓版——但 Go 用语言内建的切片 + 结构体 + for 循环完成，**不依赖任何宏膨胀**。表驱动让「加一个用例」变成「加一行数据」。

### 3.3 t.Run 子测试的进阶：并行与清理

```go
func TestParallel(t *testing.T) {
    cases := []int{1, 2, 3, 4}
    for _, n := range cases {
        n := n // Go 1.22 前子测试闭包捕获坑：需要复制变量
        t.Run("case", func(t *testing.T) {
            t.Parallel() // 标记该子测试并行
            // ... 相互独立的用例可并行提速
        })
    }
}
```

注意：`t.Parallel()` 会让用例并行执行 → 共享状态要小心（与 C++ 多线程测试同理）。

`t.Cleanup` 注册清理函数，相当于栈上 defer，但能保证**子测试结束后**执行：

```go
func TestWithFile(t *testing.T) {
    dir := t.TempDir() // 自动清理的临时目录，Go 测试最佳实践
    t.Cleanup(func() {
        // 手动清理逻辑（如删除后台进程）
    })
    _ = dir
}
```

### 3.4 基准测试 BenchmarkXxx

基准测试与单元测试共用 `testing`，函数签名 `BenchmarkXxx(b *testing.B)`：

```go
// calc_test.go
func BenchmarkDivide(b *testing.B) {
    // b.N 由工具自动调整：先小后大，保证每轮足够采样时间
    for i := 0; i < b.N; i++ {
        _, _ = Divide(1000000, 7)
    }
}

func BenchmarkDivideParallel(b *testing.B) {
    b.RunParallel(func(pb *testing.PB) { // 并行基准（多核压测）
        for pb.Next() {
            _, _ = Divide(1000000, 7)
        }
    })
}
```

运行与解读：

```bash
go test -bench=.                          # 基准所有 BenchmarkXxx
go test -bench=BenchmarkDivide            # 精确一个
go test -bench=. -benchmem -benchtime=3s  # 带内存统计，跑 3 秒

# 输出示例：
# BenchmarkDivide-8        406130772    2.905 ns/op    0 B/op    0 allocs/op
#   │             │          │             │           │          │
#   │       CPU 核数(8)  循环次数     每次耗时    每次分配字节  每次分配次数
```

- `ns/op`：每次操作耗时——**这行最核心**
- `B/op` 与 `allocs/op`：分配越少、GC 压力越小，服务端 Go 程序常盯这块

> **C++ 对照**：等价于 Google Benchmark 的 `BENCHMARK(名称)`。注意 Go 基准每次都要把工作放进 `for i := 0; i < b.N; i++`，作者绝不能自己做固定循环——`b.N` 是框架给的。

### 3.5 覆盖率：-cover

```bash
go test -cover                 # 输出覆盖率百分比
go test -coverprofile=cover.out # 输出覆盖数据到文件

# 生成 HTML 报告，浏览器逐行看哪些没测到
go tool cover -html=cover.out
```

覆盖率的理解：**覆盖率低 ≠ 测试差**，但要防止关键路径裸奔——CI 里可设阈值：

```bash
go test -coverprofile=cover.out ./...
go tool cover -func=cover.out | tail -1   # 查看总覆盖率行
```

> **C++ 对照**：相当于 lcov/gcov 的 Coverage 报告，但 Go 一条命令即可，无需额外编译选项和 gcov 工具链。

### 3.6 -race 数据竞态检测

```go
// 并发代码常见 bug：多 goroutine 读写共享变量
// 例：counter++ 由两个 goroutine 并发执行
```

```bash
# 用 -race 跑测试（编译期插桩，运行时检测竞态）
go test -race ./...

# 输出（检测到时）：
# ==================
# WARNING: DATA RACE
# Write at 0x00c0000be020 by goroutine 7:
#   ...
# ==================
```

- `-race` 有运行时开销（约 5~10 倍），**只在开发与 CI 用**，生产编译不要带
- 与 C++ 的 TSan（ThreadSanitizer）同源思想：给数据访问加影子内存

### 3.7 跳过与环境感知测试

```go
func TestSlow(t *testing.T) {
    if testing.Short() { // 配合 go test -short 标记跳过慢测试
        t.Skip("短测试模式跳过慢用例")
    }
    // 跑一段很慢的逻辑
}

func TestNeedsEnv(t *testing.T) {
    token := os.Getenv("API_TOKEN")
    if token == "" {
        t.Skip("未设置 API_TOKEN，跳过")
    }
    // 依赖外部服务的测试
}
```

```bash
go test -short ./...   # 跳过被标记的慢测试，适合 CI 快速回归
go test -v             # 看到 t.Skip 的输出 "--- SKIP"
```

### 3.8 自定义断言与 mock（极简风格）

Go 不内置 mock 框架，但接口让 mock 极简单（复习 [[01-接口interface]] 的隐式实现）：

```go
// 假设被测代码依赖一个接口
type Notifier interface {
    Send(msg string) error
}

// 手动写 mock：实现同接口
type mockNotifier struct {
    called bool
}

func (m *mockNotifier) Send(msg string) error {
    m.called = true          // 记录调用
    return nil               // 返回可控结果
}

func TestUsesNotifier(t *testing.T) {
    mock := &mockNotifier{}
    businessLogic := NewService(mock)

    businessLogic.Notify("hello")

    if !mock.called {
        t.Errorf("期望 Notifier 被调用")
    }
}
```

> **C++ 对照**：C++ 的 GMock 需要重载虚函数、写 `EXPECT_CALL` 宏；Go 靠接口隐式实现，手工 mock 就是一个十几行的小结构体。**这也是 Go 社区偏好小而专接口的原因之一**。

### 3.9 端到端 HTTP 服务测试：httptest

服务端项目用 `net/http/httptest` 起一个**内存版 HTTP 服务**，不用真实监听端口——C++ 的 Qt/QtTest 或 gmock 里做类似事要起 TCPServer，Go 内置搞定：

```go
// handler.go —— 被测对象
func helloHandler(w http.ResponseWriter, r *http.Request) {
    name := r.URL.Query().Get("name")
    if name == "" {
        http.Error(w, "缺少 name 参数", http.StatusBadRequest)
        return
    }
    fmt.Fprintf(w, "Hello, %s!", name)
}

func NewMux() *http.ServeMux {
    mux := http.NewServeMux()
    mux.HandleFunc("/hello", helloHandler)
    return mux
}
```

```go
// handler_test.go
package main

import (
    "io"
    "net/http"
    "net/http/httptest"
    "strings"
    "testing"
)

func TestHelloHandler(t *testing.T) {
    // 构造 httptest 服务器：内部起监听，用完自动关
    ts := httptest.NewServer(NewMux())
    defer ts.Close()

    // 表格驱动：cases 覆盖正常/缺参数/方法错误
    cases := []struct {
        name, query string
        wantCode    int
        wantBody    string
    }{
        {"正常", "?name=Tom", 200, "Hello, Tom!"},
        {"缺参数", "", 400, "缺少 name 参数"},
    }
    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            resp, err := http.Get(ts.URL + "/hello" + c.query)
            if err != nil {
                t.Fatal(err)
            }
            defer resp.Body.Close()

            if resp.StatusCode != c.wantCode {
                t.Errorf("code = %d, want %d", resp.StatusCode, c.wantCode)
            }
            body, _ := io.ReadAll(resp.Body)
            if !strings.Contains(string(body), c.wantBody) {
                t.Errorf("body = %q, want contains %q", body, c.wantBody)
            }
        })
    }
}
```

> **C++ 对照**：这一步相当于 C++ 里为一个 REST 服务「起一个真服务器 + 发真实请求」的集成测试。httptest 让单元与集成测试合一：**在测试进程内起服务、走完整 HTTP 栈**，不碰真端口、无外部依赖。

`httptest.NewServer` 还有两个变体：

```go
httptest.NewServer(handler)        // 完整 HTTP/1.1 监听
httptest.NewTLSServer(handler)     // HTTPS（客户端要用其 Client 证书）
httptest.NewRecorder()             // 不监听：直接捕获 handler 写入的响应
```

```go
// 用 Recorder 做纯内存验证（更快）
func TestHelloRecorder(t *testing.T) {
    rec := httptest.NewRecorder()
    helloHandler(rec, httptest.NewRequest("GET", "/hello?name=Go", nil))
    if rec.Code != 200 || rec.Body.String() != "Hello, Go!" {
        t.Errorf("got %d %q", rec.Code, rec.Body.String())
    }
}
```

### 3.10 Fuzz 模糊测试（Go 1.18+ 简述）

Go 内置 fuzzing：给一个「种子样例」，工具自动变异输入找崩溃/断言失败：

```go
// fuzz 目标函数：与单元测试同名族
func FuzzStringToInt(f *testing.F) {
    f.Add("123")   // 种子语料：默认必跑
    f.Add("-42")
    f.Add("0")
    f.Fuzz(func(t *testing.T, s string) {
        got, err := StringToInt(s)
        if err != nil {
            return // 输入非法是允许的
        }
        // 有一条不变量：合法解析出的整数再转回字符串，前缀必须可再解析
        // 例如：任何被解析成功的输入 → 至少得出 int
        _ = got
    })
}
```

```bash
go test -fuzz=FuzzStringToInt -fuzztime=5s
```

> ⚠️ **注意**：fuzz 的目标函数若对非法输入直接 `t.Fatal`，fuzzer 会立即记为一个「失败用例」。正确写法是**预期非法输入走 return**，只有「不变量被打破」才算 bug。

## 四、常见坑与误区

### 坑 1：测试函数签名写错，静默不执行

- **现象**：写了 `func TestDivide(t *testing.T)`，但 `go test -v` 里看不到它。
- **原因**：函数名不是 `Test` 开头（如 `Test_divide` 预发）；或参数类型不是 `*testing.T`；或文件不以 `_test.go` 结尾。
- **正确写法**：`func TestXxx(t *testing.T)` 三要素——大写 `Test` 前缀、`*testing.T` 参数、`_test.go` 文件名。

### 坑 2：`t.Errorf` 在致命条件后继续执行导致二次恐慌

- **现象**：`err` 为 nil 时继续解引用 `result`，panic 掩盖真实断言。
- **原因**：Errorf 不终止，后续代码假设前置条件已满足。
- **正确写法**：前置条件失败用 `t.Fatalf` 直接终止；只有纯值比较才用 `t.Errorf`。

### 坑 3：表格驱动里闭包捕获循环变量

- **现象**：子测试里打印/使用 `tt` 时所有用例都显示最后一个值（Go ≤1.21）。
- **原因**：`t.Run` 的回调是闭包，循环变量 `tt` 被捕获并复用。
- **正确写法**：Go 1.22+ 循环变量已自动为每次迭代创建新值，直接可用；老版本在循环体内 `tt := tt` 复制一份。

### 坑 4：基准测试写错 b.N，结果失真

- **现象**：Benchmark 里自己写死了循环次数，或循环内什么都不做被编译器优化掉。
- **原因**：`b.N` 必须由框架控制；空循环可能被优化成空操作。
- **正确写法**：`for i := 0; i < b.N; i++ { 被测代码 }`，且被测结果尽量存入 `result` 变量防止被优化。

### 坑 5：测试依赖真实网络/数据库，CI 反复失败

- **现象**：本地跑过，同一测试在 CI 或同事机器上偶发失败。
- **原因**：测试写死了外部服务地址，或依赖执行顺序。
- **正确写法**：外部依赖用接口抽象 + mock（见 3.8）；或 `t.Skip` 显式跳过 + 单独打 tag 的集成测试。

### 坑 6：`go test ./...` 会编译失败，因为被测代码里有用 `main` 包

- **现象**：对 `package main` 项目跑测试报「cannot import main package」或构建错误。
- **原因**：`go test` 对 main 包支持有限，且 main 包里的 `main()` 会被一起打包。
- **正确写法**：业务逻辑下沉到非 main 包测试（这也是一种项目结构驱动，见 [[03-项目结构-internal-pkg-cmd]]）；或测试文件也放 `package main` 同包即可（示例 3.1 的方式正确）。

### 坑 7：忘了 `-race`，并发 bug 在线上才爆

- **现象**：生产环境偶发数据错乱，本地正常。
- **原因**：并发竞态靠运气触发，没开检测。
- **正确写法**：CI 固定 `go test -race ./...`；本地改并发代码后先 `-race` 回归再提交。
