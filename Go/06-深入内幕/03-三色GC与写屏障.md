# 03 - 三色 GC 与写屏障

> C++ 的 RAII/智能指针是"代码到哪回收到哪"；Go 的 GC 让事情自动发生——代价是你必须理解它何时跑、怎么跑

---

## 一、简述

Go 从 1.5 开始使用**并发三色标记-清除**垃圾回收器：标记阶段与应用并发跑，通过**写屏障**保证并发下的正确性，把 STW（Stop-The-World，全停）压缩到毫秒级。本章剖析三色算法、写屏障原理、`GC 触发时机（GOGC / GOMEMLIMIT）`、`gctrace` 日志解读，以及从 C++ 视角看"自动回收"带来的确定性问题。

> **核心要点**：垃圾回收的本质是"追踪所有存活对象的引用图"。三色让追踪与程序运行并发，写屏障保证并发期间引用关系不变而漏标对象；`GOGC==100` 的意思是"堆翻倍时才触发下一次 GC"。理解这些，你才能在调优时不被玄学推着走。

---

## 二、C++ 对照速查表

| 概念 | C++ | Go | 关键差异 |
|------|-----|-----|----------|
| 生命周期管理 | `new`/`delete`、RAII、`shared_ptr` | 自动 GC | C++ 确定、Go 不确定（回收时点不定） |
| 引用计数 | 手写计数 / `shared_ptr` | 无引用计数 | Go 用可达性分析，无循环引用问题 |
| 循环引用 | `weak_ptr` 打破 | 天然解决 | 三色标记只关心可达性 |
| 悬垂指针 | `shared_ptr` 防悬垂、`weak_ptr` 观测 | 不可能悬垂（GC 保证活着就安全） | 但 `unsafe` 除外 |
| 析构时机 | 作用域结束/`shared_ptr` 归零 | 不确定（对象 GC 后才回收内存） | 需要清理副作用时必须显式 `Close` |
| 手动释放 | `delete` | *不存在（`runtime.GC()` 只建议回收） | 别依赖手工 GC |
| 触发条件 | 无 | heap 增长到阈值 / 周期 / 显式 | `GOGC`、`GOMEMLIMIT` 控制 |
| 停顿 | 无（确定性） | 少量 STW（毫秒级） | 现在基本无感，但被 K8s CPU 限流仍可能抖动 |
| 代价感知 | 手工优化分配 | 分配快、回收不确定 | 追求低延迟要控制分配率 |

## 三、逐主题详解

### 3.1 为什么要 GC：先看可达性

GC 不关心"这块内存是不是有人 stack 上引用"的细节，只关心一件事：**从根（root）出发，你能走到哪些对象？**

```
    根集合（Roots）
     ┌─────────────────────────────────────────────┐
     │  · 全局变量                                  │
     │  · 各 goroutine 的栈（局部变量、参数）       │
     │  · 寄存器中的指针                            │
     │  · 运行时内部结构（finalizer 等）            │
     └─────────────────────────────────────────────┘
                      │  通过指针字段
                      ▼
         ┌──────────────────────────┐
         │      对象图（对象+字段）  │  ← 从根可达 = 存活
         └──────────────────────────┘
```

- **可达（alive）**：从根能沿指针链走到的对象 → 保留。
- **不可达（dead）**：从任何根都走不到的 → 回收空间。
- C++ 的 `shared_ptr` 是"引用计数"，有**循环引用泄漏**且多线程计数有成本；Go 的可达性分析天然免疫循环引用，也无需原子计数。

> **C++ 对照**：`shared_ptr` 做的是"局部的、增量的"判断（这块内存引用归零我就释放）；GC 做的是"全图的、延迟的"扫描。前者局部精确但全局有漏洞（环）、后者全局精确但时点不确定。两者是不同哲学，各有适用面。

### 3.2 三色标记：白灰黑

标记过程把所有对象视为三种颜色：

```
  白色（White）      灰色（Gray）          黑色（Black）
  未被扫描          已发现但孩子未扫描     已扫描完（app期存活）
  ┌──────┐          ┌──────┐             ┌──────┐
  │  可回收 │ 发现 →  │ 待扫描 │ → 扫孩子 →  │ 已确定存活│
  └──────┘          └──────┘             └──────┘
   GC 后清空          (工作队列)            结果集
```

标记-清除算法的步骤：

```
1. 初始：所有对象都是白色
2. 从根出发，把直接引用的对象染灰（加入工作队列）
3. 循环：取一个灰色对象
        → 把它引用的所有白色对象染灰
        → 把这个对象染黑
4. 当工作队列空（没有灰色），标记结束
5. 扫描全部对象：白色 → 不可达 → 清除；黑色 → 保留
```

```
示意：            灰队列 = [A]     （根→A）
                  取 A → B、C 变灰，A 变黑
                  灰队列 = [B,C]
                  取 B → D 变灰，B 变黑
                  取 C → 无孩子，C 变黑
                  取 D → 无孩子，D 变黑
                  灰队列空 → 剩余白色 E,F,G 若不可达 → 清除
```

关键正确性条件（也是并发 GC 的难点）：**在标记过程中，不能让"一个黑对象引用一个白对象"存活下来**——否则该白对象会被误当作垃圾回收掉。

### 3.3 并发标记：真正的难点是"一边跑一边标"

如果标记全程 STW，程序会卡很久（大型堆要数百毫秒）。Go 1.5+ 的设计是：**标记阶段与程序并发执行**（`并发标记`），只有极其短暂的**开始/结束 STW**。

并发带来的危险：

```
  程序正在跑：
  A(黑) 原本引用 C(白)
  这时程序修改：A.C = nil
  然后程序又让 D(白) 被根引用；但 D 已经扫过？没被看见？
  → 若 D 成为"染白但可达"，下一轮清除会误杀！
```

`经典算法（Dijkstra 写法）`：**写屏障**——当程序执行"把白对象写进引用位置"这个动作时，额外做一件事：把被引用的白对象**染灰**（加进工作队列）。这样"新出生/新建立的引用"在标记期间立刻被纳入扫描，就不会漏标。

### 3.4 Go 的混合写屏障（Mix Write Barrier）

Go 1.8+ 用的是 **Yuasa + Dijkstra 混合写屏障**，目标是把**初始 STW（scan-start）**从"要扫全栈根+建快照"压缩到几乎为零，并在 CMS（Concurrent Mark Sweep）的思想里达到"标记期间没有完全 STW"：

- **插入写屏障（Dijkstra）**：写指针 `slot = ptr` 时，如果 `ptr` 是白色对象，将其**染灰**。防"误删后被误收"。
- **删除写屏障（Yuasa）**：写指针前，把旧值 `slot` 指向的对象染灰。防"刚被置空（变白）但可能仍被其它路径引用"。
- 混合：在 GC 标记期间**所有写操作**的 slot 上同时应用；两者的结合保证"要么旧引用被追踪、要么新引用被追踪"，黑→白引用不会存活。
- **栈上指针不启用写屏障**（对栈的写不拦，代价是 GC 开始/结束要短暂 STW 扫描栈——这正是"并行 GC 也要两次小 STW"的原因之一）。

```
            GC 时间线（Go 1.8+）
┌────────┬──────────────────┬────────┬────────┐
│ STW 扫描│  并发标记(应用在跑) │ STW 清理 │ 后台清除 │
│ 根与栈 │  灰队列处理 + 写屏障 │ 白色清除 │ 就地清扫 │
│ (很短) │   (分钟级长堆也在跑) │ (很短) │ spans    │
└────────┴──────────────────┴────────┴────────┘
   标记开始                   标记结束
```

> ⚠️ 实际上 GC 整体还分：`mark termination`（清栈上的指针，这步 STW）和 `sweep`（清理阶段可以和程序并发还能 lazy 延迟）。所以「并发 GC 不是没有 STW，而是**把 STW 压到每次几毫秒以内**」。

### 3.5 GC 触发时机：GOGC 与 GOMEMLIMIT

#### 3.5.1 GOGC（默认 100）

`GOGC` 的语义是**目标堆增长率**：当**堆大小达到「上次标记结束后存活量 × (100+GOGC)/100」**时触发下一次 GC。

```
  上次 GC 后存活的内存 = 4 MB（live）
  GOGC = 100 → 堆涨到 8 MB 时触发下一次 GC
  GOGC = 50  → 堆涨到 6 MB 时触发（更频繁，更省内存）
  GOGC = 0   → 禁用动态触发（只在手动 GC 时回收）
  GOGC = off → 彻底关闭自动 GC（实验性/特殊用途）
```

```bash
# 环境变量设置
GOGC=50 go run main.go
# 运行时设置
# 在代码里: debug.SetGCPercent(50)  // 见 runtime/debug
```

- GOGC 越大，GC 次数越少但堆峰值越高（**空间换时间**）。
- GOGC 越小，GC 越频繁，CPU 消耗在标记上增多（时间换空间）。
- 常见调优方向：**内存富余时间变大**（`GOGC=200` 或更高），减少 GC 次数换吞吐；**内存捉紧**时调小。

#### 3.5.2 GOMEMLIMIT（Go 1.19+）

`GOMEMLIMIT` 给 GC 一个**内存软上限**，让 GOGC 在有富余时 "自动变懒、快到时点变勤"：

```
        内存曲线
  ┌────────────────────────┐  ← GOMEMLIMIT（上限，软性）
  │   GC 提前触发，压回去    │
  └────────────────────────┘
                          ↑ 没碰线时 GOGC 尝鲜"多攒点"
```

```bash
GOMEMLIMIT=512MiB go run main.go
# 或代码：debug.SetMemoryLimit(512 << 20)
# 默认 = 无上限（math.MaxInt64）
```

> ⚠️ **GOMEMLIMIT 是"软"的**：它不能阻止 OOM，只是让 GC 在接近上限时更激进。页缓存、cgo 分配不计入 Go 堆，所以别把容器内存全填给它。`/gc/memlimitexceeded` 指标可以观察。

### 3.6 `GODEBUG=gctrace=1`：读懂 GC 日志

```bash
GODEBUG=gctrace=1 go run main.go
```

输出例（每一行就是一次 GC 周期，Go 1.19+ 格式）：

```text
gc 23 @0.104s 3%: 0.024+0.71+0.021 ms clock, 0.096+0.50/1.1/0+0.084 ms cpu, 18->18->10 MB, 12 MB goal, 8 P
```

| 片段 | 含义 |
|------|------|
| `gc 23` | 第 23 次 GC |
| `@0.104s` | 程序运行 0.104s 时发生 |
| `3%` | GC 累计占用的 CPU 比例 |
| `0.024+0.71+0.021 ms` | STW 前清扫 / 并发标记 / STW 收尾（clock） |
| `18->18->10 MB` | GC 前堆 / GC 后堆（标记完成）/ 存活堆 |
| `12 MB goal` | 下一次触发目标（= 存活 × 2 左右） |
| `8 P` | 8 个 P 参与并发标记 |

> 排障直觉：`goal` 长期比 `live` 大得多 = 堆涨幅大，GC 频率低；`cpu 部分`里 `tail latency` 高 = 标记阶段 CPU 竞争或在 STW 卡住了。要**更长周期**的就用 `GODEBUG=gctrace=1` 结合 `go tool trace`。

### 3.7 GC 调优直觉（先有方向再动手）

1. **别拿 gctrace 当 KPI，拿延迟/内存曲线当 KPI**。GC 每次几毫秒的停顿对「低延迟服务」通常无关紧要；真正拖垮的是"分配率太高 → GC 频次太高 → 周期性 CPU 尖峰"。
2. **降低分配率**（见 [[02-逃逸分析与内存分配]]）是 GC 压力的第一杠杆：减少 `allocs/op`，GC 自然少跑。
3. **GOGC 往上调**（200/400），牺牲内存换吞吐；**GOMEMLIMIT 设容器上限的合理比例**，让"空间富余时少跑 GC、逼近上限时多跑"。
4. **`pprof` 的 `heap` 与 `allocs` 视图**确认分配来源（见 [[05-pprof性能调优]]）。
5. 极端低延迟场景可 `debug.SetGCPercent(-1)` 关掉自动 GC + 定时 `runtime.GC()`，**但这是高维护风险的野路子**，先量数据再说。

### 3.8 写屏障到底拦谁的：一个手推例子

假设标记进行中，程序做了这样一个赋值（Dijkstra 插入屏障视角）：

```
标记前状态：
  根 ──→ A(黑) ────→ B(白)
                 └──→ C(灰) ──→ D(白)

程序现在执行：A.B = D        （把 B 换成 D）

直接后果：D 被"黑对象 A 引用"，但 D 目前是白色、又不在灰队列——
         若没屏障，D 将永远不被扫描，最后被误清除！

插入写屏障（Dijkstra）：写 A.B = D 时，发现 D 是白色 → 把 D 染灰入队
结果：D 被加入灰队列，随后被扫描染黑，误杀被避免。

删除写屏障（Yuasa）：写 A.B = D 之前，把旧值 B 染灰
         ——防止"B 换走时，B 可能在别处仍被引用"而漏标。
```

一张表总结两种屏障的语义：

| 屏障 | 触发点 | 防的故障 | Go 中的地位 |
|------|--------|----------|-------------|
| 插入屏障（Dijkstra） | 写目标时，新值被染灰 | 新引用 → 白对象成孤儿可被误收 | 堆上写生效 |
| 删除屏障（Yuasa） | 写目标时，旧值被染灰 | 旧引用消失，但对象可能仍可被其它路径到达 | 与插入结合构成混合屏障 |

Go 的混合写屏障在**堆对象**的指针字段写入上生效；**栈**不拦（扫描在两个 STW 点做，见 3.4）。这就是为什么极端少数场景 `go vet` 会提醒你把指针存进 `map` 取值等"可能绕过屏障"的写法——一般不用担心，但要知道屏障是分层设计的。

### 3.9 GC 清扫（Sweep）与"空闲终结"：不是全部立清

`清除（sweep）`阶段把标记为白（不可达）的 span 里的内存归还分配器：

- Go 采用 **lazy sweep**：不清扫则在**下次分配**时顺带扫对应的 span，避免一次全量清扫的"卡顿峰"。
- **空闲 span 会被缓存**，尽量还给 OS 用 `scavenger`：超过阈值（默认 5 分钟未用）由后台 `scavenger` 归还 OS，避免 `RSS` 虚高。
- 因此**进程 RSS 不一定立即下降**——内存可能缓存着备用；这不是泄漏，是运行时的延迟归还策略。

```bash
# 想立刻归还：触发 GC + 强制 scavenger（测试/诊断用，别进生产）
GODEBUG=madvdontneed=1 timeout 5 go run main.go
```

> **C++ 对照**：C++ 的 `malloc` 释放后内存也可能不还给 OS（glibc arena 缓存），同样是"延迟归还"。区别是 Go 的分配器自带 scavenger 有节律地归还，C++ 通常直到 `malloc_trim` 才还。

### 3.10 指针位图：GC 怎么知道对象里哪些是"指针字段"

GC 扫描对象时要知道每个对象的"指针布局"（哪个偏移是字面值、哪个是指针），否则会把 int 当指针追，追出乱棒：

```
  类型 User（编译期生成 ptrbits 位图）
  ┌──────────┬──────────┬──────────┐
  │ Name string│ Age int   │ Next *User│
  │  ptr       │ scalar    │ ptr       │
  └──────────┴──────────┴──────────┘
      1          0          1        ← 位图：1=含指针,0=纯数据
```

- 编译器在**类型本身**里记录"指针位图"（`runtime.ptrdata`、辅助 GCBitmap），GC 扫描时按位图迭代，不猜。
- **这正解释了为什么 `unsafe` 裸转换指针可能"骗过 GC"**：位图是编译期按静态类型生成的；你用 `unsafe.Pointer` 把 `*User` 转成 `*[N]byte` 后，GC 看到的位图仍是原来的（或没有），一旦这个对象回收后你又解引用，就踩到已释放内存。这也是 [[07-unsafe与cgo互操作]] 里风险部分的根源。
- `runtime.KeepAlive` 用于"我明明用过这个地址，但编译器优化掉最后使用"的罕见场景，保证指针在调用者视角里"活着"直到某个点。

### 3.11 finalizer 与 KeepAlive：GC 的"钩子"要用对

```go
package main

import "runtime"

type DB struct{ conn int }

func newDB() *DB {
	// finalizer：对象被 GC 回收时尝试"补救性关闭"（这是最后防线，不是主通道）
	d := &DB{conn: 42}
	runtime.SetFinalizer(d, func(db *DB) {
		// 仅用于"兜底"，不保证执行，也可能在别的 goroutine/时刻执行
		// close(db.conn)
	})
	return d
}

func main() {
	_ = newDB()
	_ = runtime.KeepAlive // 见下
}
```

- **引用语义**：只要对象可达，finalizer 不执行；GC 决定回收时才排队执行。
- **顺序/次数不保证**：finalizer 可能延迟、可能被跳过（`GOFLAGS`/分配压力下）、执行期间对象"复活"（又变可达）会取消回收——**别把业务清理依赖在 finalizer 上**。
- `runtime.KeepAlive(x)`：显式告诉编译器/GC "x 的指针在此时仍在使用"，防止"最后使用被优化到 `defer`/`return` 之前"导致 `x` 提前回收。典型场景：`cgo` 回调后、`unsafe` 缓冲操作后。

### 3.12 观测 GC：`runtime/metrics` 与压测时的必备指标

不靠猜，用 Go 1.16+ 的 `runtime/metrics`（或 Prometheus 的 `go_gc_*` 指标）观测 GC 健康度：

```go
package main

import (
	"fmt"
	"runtime/metrics"
)

func main() {
	// 采一个 GC 指标：最近一次 GC 的堆占用比（0 到 1，1=已到触发线）
	const desc = "/gc/heap/goal:ratio"
	samples := []metrics.Sample{{Name: desc}}
	metrics.Read(samples)
	if samples[0].Value.Kind() == metrics.KindFloat64 {
		fmt.Printf("heap 到 GC 目标的占比: %.2f\n", samples[0].Value.Float64())
	}
}
```

常用指标对照（与 `GODEBUG=gctrace=1` 的关系）：

| metrics 名 | 含义 | 对应 gctrace 片段 |
|------------|------|-------------------|
| `/gc/heap/goal:ratio` | 当前堆 / GC 目标堆 | `goal` |
| `/gc/pauses:seconds` | 每次 GC 停顿耗时分布 | `0.024+0.71+0.021` |
| `/gc/cycles/total` | GC 累计次数 | `gc 23` |
| `/memory/classes/heap/objects/bytes` | 堆上存活对象字节 | `live` |

> 压测范式：做 5 分钟压测，同时打 `gctrace` 或采集 metrics，观察"GC 停顿分布是否出现长尾、CPU 被 GC 吃掉的百分比"——有数据之后，再谈调 GOGC 还是改分配。

## 四、常见坑与误区

### 坑 1：以为 GC 会"立刻回收"，用后即依赖内存释放

**现象**：写了 `defer f.Close()` 以为文件句柄/内存马上释放？文件句柄是给 OS 的，与 GC 无关——但以为"对象死了内存马上回来"写大量一次性分配。
**原因**：GC 是延迟的、触发式的。对象变得不可达后，要等下一次 GC 触发才被清扫。
**正确认知**：显式资源（文件、锁、网络连接）**永远要 defer Close**，别指望 GC；内存回收可以接受延迟。需要确定性清理副作用的对象，实现 `finalizer` 要小心（finalizer 也延迟且顺序不定）。

### 坑 2：用 C++ 的"析构函数"思维给 Go 对象加清理逻辑

**现象**：在 Go 里写"对象不再使用时必须做 X"，结果 X 迟迟不执行。
**原因**：没有"对象销毁时自动回调"的确定性机制。`runtime.SetFinalizer` 只在 GC 回收该对象时触发，且**不保证运行时机/顺序/次数**。
**正确写法**：需要确定性清理就显式暴露 `Close()/Release()` 接口，配合 `defer`；把"释放"和"GC 回收"看作两码事。

### 坑 3：为了"不触发 GC"把 `GOGC=off`，然后 OOM

**现象**：听说关掉 GC 性能高，直接 `GOGC=off`，跑一会儿 OOM。
**原因**：GC 关了，堆无上限膨胀，直到 `mmap` 失败/容器 OOM。
**正确认知**：`GOGC=off` 只适合"生命周期极短、瞬间大量分配的 CLI"场景。长期服务用 `GOMEMLIMIT` 兜底，别裸奔。

### 坑 4：认为 GOMEMLIMIT 能防止 OOM

**现象**：容器内存 1GiB，设 `GOMEMLIMIT=1GiB`，以为绝对安全。
**原因**：GOMEMLIMIT 只管 **Go 堆**，`cgo` 分配的内存、`C.CString`、goroutine 栈之外的 OS 内存、第三方 C 库的 malloc 都不在统计内；页缓存也占内存空间。
**正确认知**：留出余量（比如容器内存的一半或 `0.8 × limit`），配合 `GOGC` 一起设置。线上用 `/debug/pprof/heap`、`/debug/gc` 观察真实占用。

### 坑 5：在热路径里调 `runtime.GC()` 或塞一个"防 GC"的大通道

**现象**：为了"帮 GC"在设计里硬塞全局缓冲池、或发信号让 GC 每毫秒跑一次，导致吞吐崩了。
**原因**：手动 `runtime.GC()` 会触发一次**同步的全停**，把 CPU 偷走做标记；反直觉地在热点塞大缓冲，只把分配挪了个地方，还增加 GC 标记负担。
**正确认知**：`runtime.GC()` 只用于测试/基准/内存统计；生产里要"GC 更省力"就减分配率或调 GOGC，而不是自己踩油门。

### 坑 6：从 C++ 迁移过来，给所有大对象包一层"池"以为能避免 GC 停顿

**现象**：`sync.Pool` 包住一个 10MB 结构，结果 GC 停顿反而变长。
**原因**：池里的对象是**可达的**（在池里就没法回收），GC 标记照样要扫它，还**永远不回收**；大对象留得越久，标记成本越高。
**正确认知**：`sync.Pool` 适合"创建昂贵又短暂"的对象（正则、临时缓冲）；大对象"短命"才是友 GC 的——创建后尽早不可达，GC 只扫一次。理解为：**池延长寿命，大对象延长寿命 = 堆更难清**。

### 坑 7：看到 gctrace 里 `goal` 与 `live` 差异大就慌

**现象**：`18->18->10 MB, 12 MB goal`，以为 `12 MB goal` 表示要涨 12MB 才回收。
**原因**：goal 是**目标**（触发值），不是"现在回收的代价"。GC 早于 goal 触发也可以（如大分配触发、GOMEMLIMIT 触发）。
**正确认知**：看趋势（goal 是否长期高、GC 频率是否过高、`cpu 3%` 是否逐年爬升），单个值没有意义。用工具（pprof、trace）看整体。

### 坑 8：把 finalizer 当"析构函数"做业务清理

**现象**：用 `runtime.SetFinalizer` 关文件/释放锁，测试有时跑不完甚至泄漏句柄。
**原因**：finalizer 是 GC 回收的**附带行为**，时机不确定、顺序不确定，且在 GC 压力下可能被推迟甚至跳过；依赖它做"必须发生"的清理是定时炸弹。
**正确写法**：所有必须的清理走显式 `Close()`/`Release()` + `defer`；finalizer 只配做"保险"（而且多数项目里连保险都不需要——它带来额外 GC 复杂度）。

### 坑 9：把普通对象指针塞进 `chan`/`unsafe` 后"忘了它仍是 GC 追踪对象"

**现象**：以为对象只是"栈变量传了一下"，结果它被函数保存在某处，GC 一直看得到，堆一直涨。
**原因**：GC 追踪的是**指针（包含隐式指针的 slice/map/chan）**，不会因为"你以为它死了"就不看。任何把指针/引用"藏"在某结构里让它长期可达，都会让对象成为 GC 眼中的存活对象。
**正确认知**：检查"堆一直涨"时，先看"什么对象长期可达"（pprof heap profile 的 live 视图），而不是"谁调了 GC"。**可达性决定存活，不是你的直觉。**

### 坑 10：在 C++ 世界里习惯的"指针 = 零成本别名"，在 Go 里可能被 GC 加倍成本

**现象**：为了"少拷贝"把大对象到处传指针，结果 GC 停顿指数上升。
**原因**：C++ 里 `T*` 只是地址；Go 里**每多一层指针都会让 GC 标记多走一条边**。大对象图、深指针链的标记成本随"引用边数"线性增长。
**正确认知**：Go 里"少拷贝"与"少边数"都有意义，但"少边数"常被忽略。扁平化（用连续切片而非指针链）、减少不必要的指针层级，是 GC 友好的写法——对照 C++，你为了缓存友好做的 AoS/SoA 变换，方向竟然一致。
